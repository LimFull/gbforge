## 1. 크래시 원인과 해결

| 증상 | 원인 | 해결 |
|---|---|---|
| 부팅 직후 ARM PC가 VRAM/OAM 영역으로 튐, IWRAM 데이터 파손 | GCC는 Thumb-1에서 tail call을 만들지 않음 → 함수 간 `JP`가 전부 중첩 호출 → 메인 루프마다 C 스택 증가 | **트램펄린**: 함수 간 JP는 `gb.jfn/jat`을 설정하고 반환, 가장 가까운 CALL 지점(또는 최상위)이 실행. 죽은 프레임(복귀 주소가 이미 pop됨)은 바깥으로 전파 |
| `no compiled entry FFFF:FF80` | DQ가 HRAM에 복사한 루틴이 기존 OAM DMA 패턴과 다름 (`LDH (C),A / DEC B / JR NZ / RET`) | HRAM 루틴 패턴 표에 네이티브 스텁 추가 |
| `no compiled entry 06:40E1` 등 | 테이블 기반 far call(`RST $10` → `JP HL`)의 대상을 정적 분석이 모름 | **CDL 피드백**: Mesen 헤드리스 실행(`scripts/mesen_cdl.py`)의 Code/Data Logger에서 JumpTarget/SubEntry를 진입점으로, 데이터 전용 구간을 data annotation으로 투입 |

CDL은 *실제 실행된 코드*의 증거로만 쓴다. 미해결 간접 분기를 "해결"로 집계하지 않으므로 strict 게이트 수치는 그대로다(계획 11.3 원칙).

## 2. 타이밍: 하드웨어 클럭 → GB 사이클 기준

원본과 프레임 단위로 비교하니 하드웨어 클럭 모델은 (a) 원본의 지연 프레임, (b) LCD 재점등 시 위상 리셋을 재현할 수 없었다. 전환:

- 생성 코드가 명령별 T-사이클을 `gb.cyc`에 누적(직선 구간 단위로 합산, 분기·IO·진입 지점에서만 반영).
- VBlank/LYC/STAT HBlank/타이머/DIV/LY/STAT 모드를 모두 `gb.cyc`에서 계산. LCD 켜짐 시 프레임 원점 리셋.
- 실시간 동기는 GB VBlank에서만(GB가 실시간보다 앞서지 않게). 늦어진 시간은 따라잡지 않는다(원본과 동일).
- 결과: 정렬 후 정상 구간에서 원본과 카운터가 프레임 단위로 일치.

## 3. 성능 작업 (DQ 로딩 구간 기준)

측정 도구: `gb2gba port --profile`(타이머 IRQ 2 kHz 샘플러, 영상 위상과 무관) + `scripts/port_profile.py`(PC → 생성 C 줄 → GB 명령). 프레임 경계 샘플링은 위상이 고정돼 편향된다는 것을 확인하고 폐기.

| 조치 | 효과 |
|---|---|
| 동적 디스패치 512칸 캐시 | 이진 탐색 32% → 무시 가능 |
| ROMX를 포인터 1개로(뱅크 전환 시 64페이지 갱신 제거) | `set_rom_bank` 11% → 0 |
| CGB 팔레트 항목 단위 갱신 | 7% → 0 |
| 페이지 테이블 메모리 접근 | 범위 검사 5단 → 1단 |
| 연결 요소 = C 함수(분기·fallthrough로 묶음) | C 함수 61,786 → 16,001, 블록 중복 제거(명령 101만 → 64만), 루프가 트램펄린 대신 goto |
| `always_inline` + 스택 빠른 경로 | 외부 호출로 남던 push/pop 40% 제거 |
| 죽은 플래그 제거(블록 단위 생존 분석) | 플래그 저장 20.2만 곳 제거 |
| LY/STAT 나눗셈 제거(`((f>>3)*9199)>>19`, 프레임 범위 정확) | libgcc 나눗셈 30% → 0 |
| 런타임 핫 함수 IWRAM ARM, WRAM bank 0–1 IWRAM | 로딩 지연 약 30% 감소 |
| LY/STAT 폴링 생략(같은 값 연속 읽기 → 다음 경계로 시간 이동) | 대기 루프 반복 축소 |

남은 비용은 DQ의 "VRAM 1바이트씩 쓰기 + STAT 대기" 루틴(`00:1A6A`/`1A57`), 큰 함수의 진입 `switch`, 런타임 IO 경로에 넓게 퍼져 있다. 원본 GB도 이 구간에서 지연 프레임을 내며, 포트는 여기에 2–11프레임을 더한다.

## 4. CGB compat 렌더러

BG 속성(VRAM 뱅크 1: 팔레트 0–7, 타일 뱅크, 뒤집기) → GBA 스크린 엔트리, BG 색 인덱스 1–4로 불투명화, 윈도우 = BG1 + WIN0, 스프라이트 = GBA OBJ(8×8/8×16, 1D, CGB/DMG 팔레트, VBlank에 OAM 복사), HDMA, `SRAM_V113` 세이브 표식.

미구현: BG 우선순위 비트(attr 7), OBJ-behind-BG, 줄당 스프라이트 10개 제한, 프레임 중간 레지스터 변경(래스터 분할), 오디오.

## 5. 검증 도구 변경

- `until`의 `eq` 정렬을 **쓰기 브레이크포인트 1회**로 교체(이전: 1프레임씩 진행+읽기 반복 → 에뮬레이터가 수백 번 멈춤). 프레임 중간의 정확한 로직 지점에서 정렬된다.
- 1프레임 입력은 Mesen GB와 Mesen GBA의 프레임 경계 위상 차이 때문에 모호하므로 시나리오 입력은 2프레임 이상 유지.
- 시나리오 `write` 단계로 원본·포트의 카트 RAM을 같은 값으로 초기화(세이브 데이터 차이로 인한 경로 분기 제거).

화면 비교는 두 에뮬레이터의 LCD 색 보정이 달라 색 값이 아닌 **색 대응(다수결 1:1)**으로 하고, 깜빡임 위상용 픽셀 허용치(`shot_tolerance`)를 시나리오별로 둘 수 있다(기본 0).

## 5.1 검증 도구 수정: Mesen GBA 장시간 제어 끊김

GBA 세션이 약 7,600프레임에서 `invalid_native_observation`으로 제어가 끊겼다. 원인은 emucap의 Mesen 패치 0023: `getControlState`가 64비트 카운터를 `lua_pushintvalue`(내부에서 `(int)` 캐스트)로 넘겨, GBA PPU 사이클이 2^31(약 7,645프레임)을 넘으면 음수가 되고 Lua 쪽 검증이 세션을 폐기했다. Mesen 프로세스는 살아 있었다(앞서 의심한 Avalonia 충돌 보고서는 종료 시점의 별개 증상). emucap `d141eda`에서 카운터를 `lua_Integer`로 넘기도록 고쳤고, 12,000프레임 연속 실행으로 확인했다. 재빌드한 호스트를 `MESEN_BIN`으로 지정해야 한다.

## 6. 경로 탐색과 정적 far call

- **탐색은 한 세션으로**(`scripts/emucap_explore.py`): emucap 세이브 상태는 명령 단위 정지가 필요해, HALT 중인 CPU를 다음 인터럽트까지 진행시킨다. 이후 입력 위상이 밀려 세이브 상태로 이어 붙인 경로는 부팅부터 재생하면 달라졌다(병사 위치, 전투 결과). 세션 하나를 열어 두고 단계를 보내며 그대로 시나리오로 기록한다.
- **리셋 단계**: `{"reset": true}`(소프트 리셋 후 정지, 카트 RAM 유지). 헤드리스 CDL 재생은 `emu.reset()`에서 스크립트가 끊겨, 리셋마다 카트 RAM을 넘겨받는 별도 실행으로 나눈다.
- **정적 far call 진입점**: `LD HL,nn / LD B,bank / RST n`에서 RST n이 B를 MBC 뱅크 레지스터에 쓰고 HL로 점프하면(DQ의 `RST $10`) 대상을 진입점으로 추가한다. DQ에서 145개, 그중 50개는 CDL에 없었다. 원본 실행에서 만나지 않은 몬스터 코드(`35:4176`)가 이것으로 해결됐다.
- 포트가 trap에 걸리거나 GB 프레임이 120 GBA 프레임 동안 늘지 않으면 실행기가 trap 위치와 함께 멈춘다(이전에는 끝없이 진행). trap 화면은 `tte_init_con()` 누락으로 글자가 안 나오던 것을 고쳤다.

## 7. 난수와 GB 타이밍

DQ1&2는 메인 루프의 대기 구간에서 난수를 돌린다(`00:02E5 CALL $120A`를 VBlank 처리기가 `C875`를 세울 때까지 반복). 32비트 상태 `C880–C883` 중 상위 워드는 한 번 달라지면 영원히 다르므로, 포트의 GB 사이클 계산이 원본과 한 번만 어긋나도 조우·전투·NPC 이동이 달라진다.

측정(원본 Mesen ↔ 포트, C890 프레임 카운터가 같은 값이 되는 명령에서 정렬):

| 조치 | 결과 |
|---|---|
| HDMA(블록당 32), HRAM OAM-DMA·IO 대기 스텁의 루프 사이클 반영 | 대기 루프 반복 수가 프레임 단위로 원본과 같은 패턴(102,102,102,101) |
| 인터럽트를 발생 시각에 처리(시계를 되돌려 처리기 실행 후 복원), CALL 복귀를 safepoint로 | VBlank 처리기의 C890 쓰기 위치가 프레임마다 고정 |
| `VBLANK_IRQ_DELAY` 43 보정 | 그 위치가 원본과 같은 dot(LY 4, dot 179) |
| CGB 부트 ROM 인계 위상(LY 146 dot 179, DIV 0xD4DE), LY/STAT 폴링 격자, APU 상태 비트 | 측정 구간에서는 변화 없음(정확성 개선으로 유지) |

정렬 시점에 원본 난수 상태를 주입하면 이후 약 120프레임 동안 상위 워드가 매 프레임 같다.

### 7.1 남은 차이의 원인

- **PPU 줄 타이밍**: Mesen CGB 기준으로 맞췄다. mode 2는 dot 4, mode 3는 84, HBlank는 256(측정 256–259)에서 시작한다. LYC 비교와 VBlank IRQ는 dot 4다. 153번 줄은 dot 6부터 LY=0을 읽고, dot 12부터 LYC=0과 일치한다. DQ는 LYC=0 인터럽트를 켜 두는데, 이 인터럽트가 444 dot 늦게 오고 있었다.
- **프레임 정지 위상**: 원본은 정렬 지점(C890 쓰기)부터 정확히 한 프레임씩 진행한다. 포트는 GB VBlank 직후(처리기 실행 전)에 멈춰서, 입력을 한 게임 프레임 일찍 받고 일찍 뗐다. 이제 정렬 때마다 GB 프레임을 세는 위치(`gb_pace_f`)를 그 지점으로 옮겨, 양쪽이 같은 GB 시각에 멈춘다.
- **인터럽트 진입 흔들림**: STAT 읽기 순서를 원본과 포트에서 하나씩 대조했다. HBlank 대기 루프는 매번 HBlank에 다시 맞춰지므로 오차가 누적되지 않는다. 남는 것은 인터럽트 진입 시각이다. 하드웨어는 인터럽트가 걸린 순간 실행 중이던 명령을 마친 뒤 진입하므로 0–20사이클씩 흔들린다. 포트는 고정 지연을 쓴다. 이 흔들림이 HBlank 대기 루프의 읽기 격자(40사이클)를 한 칸 바꾸면 처리기 끝이 최대 40사이클 달라지고, 대기 루프 반복 수와 난수가 바뀐다.
- **입력 단위 난수 동기화**: 시험했지만 효과가 없었다. 각 입력 직전에 C890 쓰기로 양쪽을 정렬하고 원본 난수를 주입했으나, 걷기 한 칸(32프레임, 스크롤로 무거운 프레임) 안에서 다시 갈라져 조우 몬스터가 달랐다. 그래서 되돌렸다.

결론: 대기 루프 난수가 원본과 같으려면 명령 단위로 정확한 인터럽트 진입이 필요하다. GBA에서는 명령마다 이벤트를 검사하는 비용이 커 포트 성능과 맞바꿔야 한다. 게임 진행에는 난수 수열이 같을 필요가 없으므로, 이 문제는 검증 방식 쪽에서 다룬다(§8).
