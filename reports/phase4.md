## 1. 소리 출력

GBA에는 GB의 네 사운드 채널이 레지스터 비트, 클럭, 주파수 공식까지 같은 형태로 들어 있다. GB 레지스터 쓰기(NR10–NR52)를 GBA 쪽 같은 레지스터(`0x4000060`–`0x4000084`)에 바이트 단위로 그대로 쓴다.

- **웨이브 RAM:** GBA는 채널 3이 재생하지 않는 뱅크에만 CPU가 쓸 수 있다. 바뀐 패턴은 채널을 트리거하거나 DAC를 켤 때 반대쪽 뱅크에 쓰고 뱅크를 바꾼다.
- **전원 직후 값:** Mesen 부트 ROM 직후 값(NR50 77, NR51 F3, NR52 F1, 채널 1 켜짐, CGB 웨이브 `00 FF` 반복)에 맞췄다.
- **확인:** DQ 포트에서 GBA `SOUNDCNT_X`의 채널 플래그(하드웨어가 직접 보고)가 채널 1–3 재생을 보여 주고, 레지스터 값이 GB 쪽과 같다. DQ P3 비교 결과는 소리 출력 전과 같다(22/25).
- emucap으로는 소리를 녹음할 수 없어, 실제로 들어 보는 확인은 사람이 해야 한다.

## 2. MBC1/2/3/5

- **MBC1:** 5비트·2비트 레지스터, 모드 0/1의 RAM 뱅크. 모드 1에서 `0000-3FFF`에 뱅크 20/40/60이 보이는 동작은 넣지 않았다. 생성 코드가 뱅크 0 읽기를 `gb_rom`에서 바로 하기 때문이다.
- **MBC2:** 내장 512×4비트 RAM(읽으면 상위 4비트가 1), 주소 비트 8로 레지스터 선택.
- **MBC3:** 7비트 ROM 뱅크, RAM 뱅크 0–3, 시계 레지스터 08–0C, 래치. 시계는 GBA VBlank(2^24 Hz 기준 280896 사이클)로 실제 시간을 세고, 카트 RAM 뒤에 자리가 있으면 SRAM에 저장한다. 게임이 꺼져 있던 시간은 셀 수 없다.
- **MBC5:** RAM 뱅크(0x4000-0x5FFF). 럼블 비트는 무시한다.
- **카트 RAM:** GBA SRAM 32 KiB를 그대로 쓴다. 그보다 큰 카트는 `port`가 종료 코드 4로 거절한다.
- **상태 주입:** RAM 뱅크를 `GbInject`의 빈 바이트에 넣었다. Mesen의 MBC1은 5비트·2비트 레지스터를 따로 보고하므로 합쳐서 넘긴다.

## 3. RAM에서 실행하는 코드

mooneye MBC 테스트는 ROM 뱅크를 바꾸는 동안 실행할 코드를 RAM(`C000`, `FF80`)에 복사해 둔다. 실제 게임에도 흔한 방식이다. 정적 변환기는 RAM의 내용을 미리 알 수 없다.

1. **기록:** CDL을 만드는 원본 실행(`mesen_cdl.lua`)이 RAM(`8000-FFFE`)에서 실행된 명령마다 PC와 그 자리의 4바이트를 `OUT.cdl.ram`에 남긴다.
2. **ROM에서 찾기:** `gb2gba port`가 실행된 명령을 연속 구간으로 묶는다. 명령 길이는 SM83 표로 계산한다. 그 바이트열을 ROM에서 찾아 `--overlay RAM:뱅크:주소:크기`로 분석기에 넘긴다. gb-recompiled의 RAM overlay 기능이 그 ROM 바이트를 RAM 주소의 코드로 분석한다. 실행된 RAM 명령은 모두 진입점으로도 넘긴다. 분석기가 RAM 주소로 가는 `CALL`을 정적 목적지로 보지 않기 때문이다.
3. **실행:** 포트가 RAM 주소로 점프하면 `gen/overlays.c`의 표에서 해당 구간을 찾는다. RAM 내용이 그 ROM 바이트와 같을 때만 컴파일된 함수를 부른다. 다르면 이전처럼 멈춘다(trap).

함께 고친 것: CDL에서 "실행되지 않은 바이트 바로 뒤의 실행된 바이트"는 항상 명령의 시작이므로 진입점으로 넣는다. `CALL print` 뒤에 문자열을 두고 문자열 다음으로 돌아오는 방식(mooneye의 "Test OK" 출력)이 이것으로 해결된다.

## 4. 화면 중간 레지스터 변경

포트의 GB 코드는 GBA 화면 주사와 맞춰 돌지 않는다. 그래서 레지스터를 쓴 순간 GBA 레지스터를 바꾸면 줄 단위 효과(상태바 분할, 창 켜고 끄기, 물결 효과, 맵 전환)가 깨진다.

- **기록:** LCDC, SCY, SCX, WY, WX를 쓰면 그 값이 몇 번째 GB 줄부터 적용되는지 기록한다. 그리기(모드 3) 전이면 그 줄, 그 뒤면 다음 줄, VBlank 중이면 다음 프레임 첫 줄이다.
- **표 만들기:** GB 프레임의 VBlank에서 줄마다 GBA 값을 만든다. 대상은 BG0–3 스크롤, DISPCNT, BG0–3CNT, WIN0H이고, 창 내부 줄 카운터를 따라 창의 세로 위치를 정한다. 표는 두 벌을 번갈아 쓴다.
- **재생:** GBA VBlank에서 0번 줄 값을 직접 쓰고, 나머지 줄은 HBlank DMA 0–3이 줄마다 넣는다.
- **맵 변형:** 맵마다 8000 주소 방식, 8800 주소 방식, 단색(색 0) 세 가지를 미리 만들어 둔다. 그래서 LCDC의 맵·타일 주소 선택을 줄마다 바꿀 수 있다.
- **GBA 하드웨어 특성 두 가지:**
  - DMA로 `DISPCNT`–`BG1CNT`를 한 번에 쓰면 그 사이의 `DISPSTAT`도 덮어써서, VBlank 인터럽트가 꺼지는 프레임이 생겼다. 레지스터별로 DMA 채널을 나눴다.
  - GBA는 `DISPCNT`로 켠 배경 레이어를 몇 줄 뒤에야 보여 준다. 레이어는 늘 켜 두고, 창은 `WIN0H`로, DMG의 BG 끄기는 흰 맵으로 처리한다.
- **LYC:** 게임이 LYC 인터럽트 처리기에서 LYC를 다음 줄로 다시 쓰면, 같은 프레임 안에서 다시 울려야 한다. 이전에는 프레임당 한 번만 울렸다.

## 5. 스프라이트 우선순위

GBA 배경 레이어 네 개의 역할:

| 레이어 | 내용 | 우선순위 |
|---|---|---|
| BG0 | 배경 색 1–3 | 2 |
| BG1 | 창 색 1–3 | 2 |
| BG2 | 배경 색 0 (단색 타일, 타일의 팔레트) | 3 |
| BG3 | 창 색 0 | 3 |

- 일반 스프라이트는 우선순위 2로, 같은 우선순위에서는 스프라이트가 위에 그려진다. OAM bit 7 스프라이트는 우선순위 3으로 색 0 위, 색 1–3 아래에 그려진다.
- 창 영역(WIN0)은 BG1/BG3, 나머지(WIN1)는 BG0/BG2만 보인다.
- **DMG 정렬:** DMG는 X가 작은 스프라이트가 위에 온다. GBA OAM에 넣을 때 GB X 순으로 정렬한다.
- **줄당 10개:** GB는 한 줄에 OAM 순서로 처음 10개만 그린다. GBA는 스프라이트를 줄 단위로 숨길 수 없어서, 덮는 모든 줄에서 빠지는 스프라이트만 숨긴다.
- **스프라이트 크기:** LCDC.2는 스프라이트가 시작하는 줄의 값을 쓴다.
- **미지원:** CGB 타일 우선순위(BG attr bit 7: 그 타일의 색 1–3이 모든 스프라이트 위). 다섯 번째 레이어가 필요하다.

## 6. IWRAM 부족

디버그 빌드가 멈춘 원인을 찾다가 IWRAM(32 KiB)이 가득 차 스택이 데이터 영역과 겹쳐 있는 것을 발견했다.

- 함정 화면의 `tte_printf`가 stdio를 끌어들여, newlib의 파일 핸들 표 4 KiB가 IWRAM에 들어가 있었다.
- `tte_write`로 바꿔 stdio를 빼자 스택 여유가 거의 0에서 약 6 KiB가 됐다.
- DQ도 같은 상태였다(스택 여유 약 1 KiB).

### DQ1&2 (P3 시나리오, 상태 주입 비교)

25개 중 24개 일치(이전 22–23개). 남은 차이는 성 입구 페이드 도중 화면 하나로, LCD를 끄는 로딩 뒤 1프레임 문제(phase3 §8)다. 세이브 데이터(`cart_ram`)와 인트로(`n8`)도 이제 일치한다. 이유는 아래 §7.1의 정확한 멈춤 지점이다.

중간에 `k1`/`k2`(왕의 대사)가 잠시 달라졌다. 원인은 MBC 코드가 ROM 뱅크를 바꿀 때마다 카트 RAM 페이지 표를 다시 쓴 것이었다. DQ는 원거리 호출마다 뱅크를 바꾸므로 포트가 느려졌다. 포트가 느리면 GBA 프레임 단위로 멈추는 검증기가 GB 프레임 중간에 입력을 넣게 되어 대사 진행이 어긋났다. 이것은 런타임에서 고쳤고(RAM 상태가 바뀌는 쓰기에서만 매핑), 검증기도 고쳤다(§7.1).

### 7.1 검증 속도

DQ P3 비교(포트만, 원본 재사용)는 15–17분에서 약 5.5분으로 줄었다.

| 변경 | 시간 |
|---|---|
| 이전 (실제 속도, GBA 프레임 단위 진행) | 약 15–17분 |
| emucap 속도 제한 해제 (`debug` → `execution_speed: unlimited`, 약 1.9배) | 868초 |
| GB 프레임 카운터에 값 조건 쓰기 브레이크포인트: 단계마다 한 번 멈춤 | 671초 |
| 포트 입력 예약표 (`gb_script`): 관찰 지점 사이의 단계와 입력을 한 번에 진행 | 333초 |

- 시나리오는 시간이 아니라 프레임을 세므로, 에뮬레이터 속도를 올려도 결과는 같다.
- 브레이크포인트 방식에서는 포트가 항상 GB 프레임 틱에서 멈춘다. 그래서 포트가 느린 구간에서도 입력이 같은 GB 시점에 들어간다. 이전에는 GBA 프레임 단위로 진행하다 프레임 중간에 멈출 수 있었다.
- 입력 예약표는 런타임의 `{GB 프레임, 키}` 32칸 표다. 포트가 프레임 틱마다 해당 칸의 키를 `gb_keys`에 넣는다. 검증기는 스크린샷, 메모리 읽기·쓰기, 체크포인트, `until`, 리셋에서만 멈춘다.
- `scripts/test_roms.py`는 원본의 CDL과 스크린샷을 다시 만들지 않는다(원본은 결정적). 재실행은 테스트 ROM 하나에 약 15초다(이전 1–2분).
